# INT955 / INT955B — the settlement return path

## What it does `[CO:02 §4 Stage 08]`
- **INT955** is **the Kyriba ↔ Oracle Payments integration that delivers payment acknowledgements into Oracle** `[USER:2026-09-30]`; runs **hourly**. `[CO:02 §4 Stage 08]`
- **INT955B** makes bank rejections **cancel** the corresponding Oracle bank transfers and payments (payments become `VOIDED` in Oracle — observed). `[DATA:payments-status-report]`
- Rejections land in Payables as `ORA_AP_BANK_ACK_RJCT` (one of the slowest hold families). `[CO:02 §4 Stage 06]`

## Oracle-standard alternative (26C)
Oracle Payments provides **disbursement acknowledgment processing** (ISO 20022 predefined payment systems). Its settings include an automatic retrieval interval, an **Automatic Voiding Option** ("whether rejected payments are automatically voided") and acknowledgment file formats. `[ORA26C:implementing-payables-invoice-to-pay p.220]`

**INT955 does not use this feature.** It writes the acknowledgement onto custom payment DFFs through the Payables REST API (see the technical design below). So the standard feature is a modernisation option, not current state. `[CO:KYRIBA-DOC §11.3]` (resolves Q-PAY-3)

## Technical design (INT955) `[CO:KYRIBA-DOC §11]`
| Attribute | Value |
|---|---|
| OIC name | "Kyriba Payment Ackn to Oracle Inbound": a **Scheduler** integration and a **Main** integration |
| Mode | Scheduled, file-based, asynchronous batch, plus on-demand runs from the VBCS Launchpad |
| Cadence | Designed as daily 18:00 PST; **hourly** in production |
| Source | Delimited `.txt` file that Kyriba places in its SFTP `/out` folder |
| Integration user | `erp_integration` |

**Source file fields:** Bank Name, Account Number, Kyriba Reference ID (= Oracle Batch ID), Check Number, Checkrun Name, Payment Date, Acknowledgement Status, Rejection Reason, Acknowledgement Date.

**Processing:**
1. The **Scheduler** reads its metadata from the ATP table `XXCO_INT_METADATA_TBL` (keyed by RICE ID) and lists the Kyriba SFTP folder. If a file is there, `INT000 Common File Movement Inbound` moves it into OCI Object Storage, and the Scheduler then calls **Main**.
2. **Main** transforms the file, then derives the internal `check_id` with the BIP report **`INT955 GET CHECK ID REPORT`** (parameters `p_checkrun_name`, `p_check_number`). This step is needed because the check number alone is **not unique** in `AP_CHECKS_ALL`.
3. **Record classification:** a Checkrun Name that starts with `30` and is 15 characters long is a **bank-transfer** record; anything else is a **payment** record. The class decides whether the record goes to the payment update or to the bank-transfer cancellation (INT955B).
4. Main updates the payment DFFs through REST `payablesPayments/{CheckId}`, archives or errors the file, notifies through `INT000 Common Log and Notify`, and logs the run to DPulse (`DGTL_PLS.XX_IMD_INTEGRATION_ACTIVITY_T`).

**Payment DFFs updated (`AP_CHECKS_ALL`, Payment Information context):**
| Column | Segment | Content |
|---|---|---|
| `ATTRIBUTE1` | Oracle BatchID | Kyriba reference ID, kept for reconciliation |
| `ATTRIBUTE3` | Rejection Reason | A **placeholder** reason. Kyriba can't put the real bank reason in the file, so it **emails** the real reason to the business separately |
| `ATTRIBUTE4` | Acknowledgment Status | Value set `ACPT` / `RJCT`, stored exactly as received |
| `ATTRIBUTE5` | Acknowledgment Date | The date the bank processed the payment |

**Objects:**
- BI data model and report `INT955 GET CHECK ID` under `/Custom/Company/Implementation/AP/Interfaces/INT955/`.
- OIC connections: ATP DB, SFTP, OCI Object Storage, `ERPReportService` (SOAP BIP), ERP REST.
- Library `XMLLiteralReplaceFunction`.
- OCI paths: `Implementation/Inbound/AP/INT955/{Process, Archive/YYYY-MM-DD, Error/YYYY-MM-DD}/RUN-ID_Filename_YYYYMMDD_hhmmss.txt`.

**Error handling:**
- **No file** → the run is logged and ignored.
- **File can't be read** → the support group is notified and the run stops.
- **Transformation error** → the flow aborts.
- **ERP unreachable** → retried 3 times, then an email.
- **REST failure** → the file moves to Error and an email with the ERP logs goes out.
- **Per-record update error** → an email describing each failed record.

Recipients are the person who triggered the run plus `XXCO_INT_METADATA_TBL.NOTIFICATION_EMAIL_IDS_TECH`. Success emails carry total, accepted and rejected counts.

**Reprocessing:**
- **Through OIC:** move the file from Error back to Process, then run the Scheduler with the scheduler instance ID (the filename prefix before the underscore).
- **Through the VBCS Launchpad:** choose *INT955 Kyriba Payment Acknowledgment Integration*, upload the error file and submit. This calls Main directly, which recognises `RawData_` in the filename.

## INT955B `[CO:KYRIBA-DOC §6, §12.1]`
INT955B is event-driven. On a bank rejection it cancels the matching Oracle **bank transfer** or **payment**, using the checkrun-name rule above to tell them apart. It isn't documented beyond that, and its design document wasn't among the sources.

## Data returned (as seen in the payment-status report) `[DATA]`
`batch-id` (Kyriba batch), `ack-status` (`RJCT` observed), `ack-date` (`DDMMYYYY`), `bank-msg` (free text with bank reason codes). See `operations/payment-status-reference.md` for the rejection taxonomy.

## Success definition
A payment the beneficiary bank **returns** but whose acknowledgement is consumed correctly is a **systems success**. The real test when standing up a payment method is that ack and return files are received and consumed end-to-end. `[CO:02 §4, §5]`

## Gaps
- **Payment-level acks arrive only if the whole file or batch was accepted.** If Kyriba or the bank rejects the file or batch, Oracle gets no ack for any payment in it, and the payments never reach the bank. `[CO:KYRIBA-DOC §5.3, §13.1]` See FM-PAY-08…10.
- **Status values:** the DFF value set is `ACPT`/`RJCT`, but the exception-monitoring deck uses `ACCP`. Both mean accepted; the value set is the authoritative list. `[CO:KYRIBA-DOC §5.2]`
- **No acknowledgement = the bank has not received the payment.** Either a transmission issue occurred (Oracle → Kyriba → bank) or the payment is still in the process of being sent. In both cases the bank does not have it `[USER:2026-09-30]`. Example: 17-Jul-2026 BR TED/Boleto and MX runs showing `NEGOTIABLE` with empty ack fields. `[DATA]` → treat as an **actionable alert**, not noise; see FM-PAY-05.
- `RETURNED` (post-acceptance) vs `REJECTED` vs `NOT SENT` states are named in the Returned Payments epic; only `RJCT` is visible in the extract. `[CO:FIN-24248 review]`
